# מדיניות הנתונים הציבורית של HebOCRBench

**מעמד:** נורמטיבי עבור מהדורת 1.0 ומעלה.

## 1. מטרה

HebOCRBench נועד להיות תשתית ציבורית, רחבה ושימושית להערכת OCR ו־HTR בכתב עברי. מטרתו אינה לייצר חבילת דוגמה קטנה שקל להוריד, אלא למדוד מערכות מול המגוון האמיתי של מסמכים, תקופות, שפות, פריסות ואיכויות צילום שבהם משתמשים נתקלים.

לכן:

> **גודל המקור, עלות האחסון או אופן ההפצה אינם קריטריון להוצאת מקור מן הבנצ׳מרק.**

מקור נכנס או יוצא לפי ערכו המדעי, איכות ה־ground truth, אמינות ה־provenance, יכולת השחזור וההתאמה למסלול ההערכה.

## 2. הכלל המרכזי: הכללה מדעית אינה זהה להפצת בתים

לכל מקור נקבעים שני סטטוסים נפרדים:

1. **`benchmark_inclusion`** — האם המקור נכלל בפרופיל מדעי רשמי ובאיזה track.
2. **`delivery_mode`** — כיצד המשתמש מקבל את קובצי המקור.

אין להסיק מאחד על האחר. מקור שאינו ניתן למירור ישיר יכול עדיין להיות מקור מלא בפרופיל המדעי, באמצעות הורדה פדרטיבית ומאומתת מן המקור הסמכותי.

## 3. מצבי מסירה

### 3.1 `bundled`

המקור או shard שלו ניתן להפצה ישירה. הוא מופץ באמצעות GitHub Releases או אחסון אובייקטים, בצירוף:

- checksum;
- גודל;
- inventory;
- attribution;
- רישיון המקור;
- dataset/source fingerprint.

### 3.2 `federated`

הקבצים נמשכים מן המקור הסמכותי, למשל:

- Zenodo;
- GitHub/GitLab release או commit;
- MediaWiki/Commons API;
- IIIF manifest;
- מאגר מוסדי;
- URL קבוע בעל checksum.

ה־materializer חייב:

- לנעול URL, revision, record או manifest;
- לאמת checksum וגודל כאשר זמינים;
- לשמור acquisition evidence;
- להיכשל אם המקור השתנה באופן בלתי מוסבר;
- לא להחליף מקור חסר בדוגמה סינתטית.

### 3.3 `acceptance-required`

כאשר המקור דורש אישור מפורש של תנאי שימוש, הבונה מאשר אותם באמצעות פעולה מתועדת. האישור אינו משנה את תנאי המקור ואינו הופך אותו למקור שאפשר למרר מחדש ללא מגבלה.

המקור עדיין רשאי להיות חלק מלא מן הפרופיל המדעי.

### 3.4 `access-controlled`

כאשר הנתונים זמינים רק לבעלי הרשאה:

- הקוד, ה־adapter, ה־schema, ה־split policy, מדדי ההערכה וה־manifest template נשארים ציבוריים;
- המשתמש מספק root מורשה מקומי;
- נוצר fingerprint מקומי מאומת;
- תוצאה רשמית חייבת להצהיר במדויק איזו מהדורה ואילו bytes שימשו.

מסלול כזה אינו יכול להיקרא אוניברסלי אם אין לאחרים דרך סבירה לקבל הרשאה, אך אין למחוק את קיומו או את התמיכה בו.

### 3.5 `metadata-only`

מקור שאין לו ground truth אמין, גישה יציבה או תנאי שחזור מספקים נשמר ב־registry כמועמד כיסוי בלבד. הוא אינו נספר בציון רשמי עד שיעבור את השערים. הסיבה היא חוסר ראיות, לא גודל.

## 4. פרופילים רשמיים

### 4.1 `public-full-v1`

זהו הפרופיל המדעי הציבורי הקנוני. הוא כולל את כל מקורות v1 שעברו:

- source verification;
- converter validation;
- annotation/GT validation;
- split isolation;
- duplicate and leakage audit;
- track compatibility;
- license and attribution recording;
- reproducible materialization.

חברות בפרופיל אינה תלויה במצב המסירה.

### 4.2 `redistributable-v1`

זהו subset נוח של bytes שניתן למרר ישירות. הוא נועד להורדה מהירה, CI ודוגמאות. אסור להציג את תוצאותיו כאילו הן תוצאות `public-full-v1`.

### 4.3 פרופילים חלקיים

כל profile חלקי חייב:

- לקבל שם שונה;
- לקבל fingerprint שונה;
- לפרסם את רשימת המקורות המדויקת;
- לא להשתמש בתווית `full`;
- לא להופיע בראש leaderboard של הפרופיל המלא.

## 5. מקורות גדולים

אין תקרת גודל מדעית. במקום להוציא מקור גדול:

- מפצלים אותו ל־shards דטרמיניסטיים;
- מפרסמים manifest ו־checksums לכל shard;
- משתמשים ב־HTTP range/resume כאשר אפשר;
- תומכים ב־cache מקומי;
- מבצעים deduplication ברמת התוכן;
- שומרים image/GT pairs יחד מבחינה לוגית;
- מאפשרים materialization לפי track או split בלי לשנות את זהות הפרופיל הכולל.

GitHub source control אינו משמש כמחסן לקבצי corpus גדולים. זו אינה סיבה להשמיטם; זו סיבה להשתמש בערוץ מסירה מתאים.

## 6. רישיונות וייחוס

HebOCRBench אינו מאחד רישיונות שונים לרישיון חדש אחד. לכל מקור נשמרים:

- בעלים/יוצרים;
- ציטוט;
- URL סמכותי;
- נוסח רישיון או תנאי שימוש;
- חובות attribution;
- מגבלות redistribution;
- חובות ShareAlike כאשר קיימות;
- provenance של הקובץ שנמדד.

רישיון התוכנה חל על קוד HebOCRBench בלבד. הוא אינו מרשה מחדש יצירות צד שלישי.

**כוונה ציבורית וללא מטרות רווח מחזקת את מטרת הפרויקט, אך אינה משמשת כתחליף לתיעוד תנאי המקור.** הפתרון למקור שאינו ניתן למירור הוא מסירה פדרטיבית או גישה מורשית — לא מחיקה מן הבנצ׳מרק ולא הצהרה שהמגבלה אינה קיימת.

## 7. אמת־מידה ציבורית

כדי שתוצאה תיקרא רשמית, עליה לכלול:

- benchmark version;
- profile fingerprint;
- track fingerprint;
- dataset fingerprint;
- רשימת מקורות;
- evaluator version;
- model version;
- prompt/configuration כאשר רלוונטי;
- כשלי acquisition או inference;
- runtime environment;
- output bundle hash.

אם מקור חובה חסר, הבנייה נכשלת או מקבלת זהות profile אחרת. אין `best effort` שממשיך תחת אותו שם.

## 8. test נסתר

הפרויקט הציבורי יכול להחזיק test gold נסתר כדי להגן על leaderboard, אך עליו לפרסם התחייבות קריפטוגרפית ל־test set ולשמור:

- participant pack ציבורי ללא טקסט test;
- organizer pack נפרד;
- HMAC/opaque IDs;
- zero-leakage audit;
- מדיניות רענון וגרסאות;
- תהליך שחזור מבוקר.

הסתרת test gold אינה הופכת את שיטת ההערכה לפרטית: schema, scorer, track, source families ומדיניות הדגימה נשארים ציבוריים.

## 9. מקורות חדשים

בקשת הוספת מקור נבחנת לפי:

1. תרומת כיסוי ייחודית;
2. איכות ואמינות ground truth;
3. provenance יציב;
4. אפשרות לבנות split חסין־דליפה;
5. אפשרות לתעד תנאים וייחוס;
6. אפשרות לשחזר acquisition או לספק access adapter;
7. התאמה למסלול קיים או הצדקה למסלול חדש.

`המקור גדול מדי` ו־`אי אפשר להכניס אותו ל־Git` אינם נימוק לדחייה.

## 10. עקרון אי־התחזות

HebOCRBench יעדיף תמיד כשל גלוי על פני ציון מטעה:

- מקור חסר אינו מוחלף בשקט;
- עמוד שנכשל אינו נזרק מהמכנה;
- timeout נרשם ככשל;
- corpus חלקי אינו נקרא full;
- subset שנוח להפצה אינו מוצג כבנצ׳מרק כולו;
- סינתטיקה אינה מוצגת כתחליף לנתונים אמיתיים.

זהו תנאי בסיס למהדורת 1.0.
